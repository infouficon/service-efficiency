# SES → FileMaker (FMP): คู่มือสำหรับทีม FMP

เอกสารนี้สำหรับทีม FileMaker (FMP) โดยเฉพาะ อธิบายว่า SES ส่งอะไรให้ FMP ส่งเมื่อไหร่ ทำไมต้องทำ สคริปต์ `ses` ที่มีอยู่ใช้ได้แค่ไหน
ต้องปรับอะไรบ้าง และ FMP แจ้งผลกลับมาที่ SES ได้อย่างไร (รวมถึงตอนเปิด/ปิดบิล)

- รายละเอียดทางเทคนิคฉบับเต็ม (อังกฤษ): [fmp-outbound.md](fmp-outbound.md)
- การตัดสินใจที่เกี่ยวข้อง: D88–D96 ใน `docs/decisions.md`
- อัปเดตล่าสุด: 2026-11-03 (D97: อุปกรณ์เสริมไม่ส่งเป็นรายการ หน้าร้านเพิ่มใน FMP เอง · D98: **ทีม SES แก้สคริปต์ `ses` ให้แล้ว** ดู [fmp-scripts/](fmp-scripts/README.md))

## 1. ทำไมต้องเชื่อม

ที่หน้าร้าน ลูกค้าเลือกสินค้ากับพนักงาน (STAFF) แล้ว STOCK ไปหยิบของ เมื่อ STOCK กด **"ส่งสินค้าไปที่แคชเชียร์"** ใน SES ข้อมูลออเดอร์
(สาขา เบอร์ลูกค้า สินค้าหลัก จำนวน **Serial Number ของทุกเครื่อง** วิธีชำระเงิน) จะถูกส่งเข้า FMP ทันที **อุปกรณ์เสริมไม่ถูกส่งเป็นรายการในบิล**
หน้าร้านเพิ่มเองใน FMP (ส่งมาเป็นข้อมูลอ้างอิงเท่านั้น) เพื่อให้สคริปต์ `ses` เปิด **บิลพัก** ไว้รอแคชเชียร์
แคชเชียร์ไม่ต้องพิมพ์รายการซ้ำ และ SN ในบิลตรงกับเครื่องที่ STOCK หยิบจริง

## 2. การเชื่อมต่อ (ฝั่ง SES ตั้งค่าไว้แล้ว)

| เรื่อง | ค่า |
| --- | --- |
| เซิร์ฟเวอร์ / ฐานข้อมูล | `pos.uficon.net` / `UFService` (FileMaker Data API) |
| บัญชี | `ses` (ใช้เฉพาะงานนี้) |
| Layout / ฟิลด์ | `ses` / `ses_body` (ข้อความ JSON ทั้งก้อน) |
| สคริปต์ | `ses` โดย parameter = **reference ของออเดอร์** (เช่น `SES-20261103-000001`) เปิดใช้แล้วตั้งแต่ 2026-11-03 01:55 |
| ส่งเมื่อ | STOCK กดส่งสินค้าไปแคชเชียร์ (ถ้าแคชเชียร์ตีกลับแล้ว STOCK ส่งใหม่ ก็ส่งอีกครั้ง) |
| ความถี่ | SES เช็กคิวทุก 10 วินาที ต่อรอบ: login 1 ครั้ง ส่ง แล้ว logout |
| ถ้า FMP ล่ม | ลองใหม่หลัง 1, 2, 5, 10, 20, 30, 60 นาที (รวม 8 ครั้ง) จากนั้นรอ ADMIN กด "ส่งซ้ำ" |

**หนึ่งออเดอร์ = หนึ่ง record:** ส่งครั้งแรก SES สร้าง record ใหม่ ส่งครั้งต่อไปของออเดอร์เดิม (แคชเชียร์ตีกลับแล้วสแกนใหม่ หรือ ADMIN กดส่งซ้ำ)
SES **แก้ record เดิม** แล้วสั่งสคริปต์ `ses` ใหม่ ถ้าครั้งก่อนส่งไปถึง FMP แต่ SES ไม่ได้รับคำตอบ (เช่น สคริปต์ทำงานนาน) SES ค้น record ของ
reference นั้นก่อน ไม่สร้างซ้ำ ตาราง `ses` จึงมี `ses_id` ละ 1 record ตามที่สคริปต์ต้องการ SES รอคำตอบของสคริปต์ได้ไม่เกิน 60 วินาที

## 3. ข้อมูลที่ส่ง (`ses_body`)

```json
{
  "source": "SES",
  "version": 1,
  "test": false,
  "createdAt": "2026-11-03T14:40:12+07:00",
  "event": "SENT_TO_CASHIER",
  "outboxId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "queuedAt": "2026-11-03T07:40:12.123Z",
  "branch": { "code": "ISTA", "name": "iStudio @ Terminal 21 Asok" },
  "reference": "SES-20261103-000001",
  "queue": "A012",
  "state": "SENT_TO_CASHIER",
  "customerPhone": "0812345678",
  "staffId": "1004",
  "confirmedAt": "2026-11-03T07:20:03.411Z",
  "items": [
    { "partNo": "MGEA4TH/A", "upc": "195950714883", "name": "MacBook Pro M5 Pro 16 inch …", "quantity": 1, "sn": ["SML4K3429G5"] }
  ],
  "accessories": [],
  "accessoriesForCashier": [{ "name": "Case", "quantity": 1 }],
  "payments": ["0% Credit Card"],
  "paymentTypes": ["บัตรเงินผ่อน"],
  "ontop": ["AIS"],
  "points": ["MCard"],
  "burnPoints": [],
  "posBillNo": null
}
```

| ฟิลด์ | ความหมาย |
| --- | --- |
| `reference` | รหัสออเดอร์ของ SES (ไม่ซ้ำ) = `ses_id` และเป็น parameter ของสคริปต์ |
| `queue` | เลขคิวที่พนักงานเรียกลูกค้า (เช่น A012) ซ้ำได้ข้ามวัน |
| `version` | เวอร์ชันของรูปแบบข้อมูล ตอนนี้ = 1 จะเปลี่ยนเมื่อความหมายของฟิลด์เปลี่ยนเท่านั้น |
| `test` | `false` = ออเดอร์จริงเสมอ |
| `createdAt` | เวลาที่ส่ง **เวลาไทย มี +07:00** (สคริปต์อ่านตัวเลขตามที่เขียน) |
| `event` | `SENT_TO_CASHIER` (ส่งถึงแคชเชียร์) หรือ `RESEND` (ADMIN สั่งส่งซ้ำ) |
| `outboxId` | รหัสของข้อความแต่ละครั้ง (ส่งซ้ำได้รหัสใหม่) |
| `branch.code` | รหัสสาขา **ตรงกับ `branch_code` ของ ERP** (SES ลบสาขาที่รหัสไม่ตรงทิ้งแล้วเมื่อ 2026-11-03) |
| `customerPhone` | เบอร์ลูกค้า 10 หลัก (ข้อมูลส่วนบุคคล) |
| `staffId` | รหัสพนักงานที่ดูแลลูกค้า (พนักงานจาก ERP เป็นตัวเลข) |
| `items[].partNo` | Apple part number = `product_model` ใน FMP |
| `items[].upc` | บาร์โค้ด UPC จาก warroom (อาจเป็น `null`) |
| `items[].sn` | **Serial Number ที่ STOCK สแกน ไม่ซ้ำกัน เป็นตัวพิมพ์ใหญ่** ตามที่สแกนจากกล่อง (Mac/iPad ขึ้นต้นด้วย `S`, iPhone เป็น IMEI) ปกติครบตาม `quantity` |
| `items[].snMissing` | **(ใหม่ 2026-11-05)** จำนวนเครื่องที่ STOCK ส่งมาโดยยังไม่มี SN (เลือก "ส่งโดย SN ยังไม่ครบ" เช่น เครื่องโอนมาถึงร้านแล้วแต่ FMP ยังไม่รับโอน) ปกติ = 0 |
| `accessories` | **ว่างเสมอ** (`[]`) สคริปต์จึงไม่ปฏิเสธ |
| `accessoriesForCashier` | อุปกรณ์เสริมที่ลูกค้าเลือกใน SES (ชื่อ + จำนวน ไม่มี SKU ไม่มี SN) **ไว้ดูเท่านั้น** หน้าร้านเพิ่มลงบิลเองใน FMP สคริปต์ไม่ต้องอ่าน |
| `payments` | ชื่อช่องทางชำระตามที่ SES ตั้ง (ADMIN เพิ่มได้เอง เช่น `PayNext`, `WEB`) |
| `paymentTypes` | **ประเภทการชำระตามรายการของ FMP** (เงินสด, โอนเงิน, บัตรเครดิต, บัตรเงินผ่อน, ใช้มัดจำ, Trade In, U-Joy, Partner Mall, อื่นๆ) แต่ละประเภทครั้งเดียว |
| `ontop` / `points` / `burnPoints` | โปรโมชั่นเครือข่าย / สะสมแต้ม / ใช้แต้ม (U-Joy อยู่ที่นี่ ค่า `UJOY`) |
| ราคา | **ไม่มี** SES ไม่เก็บราคา บิลต้องใช้ราคาจาก FMP (สคริปต์ทำอยู่แล้ว) |

## 4. สคริปต์ `ses` / `ses_fail` ต้นฉบับ (v1): ใช้ได้แค่ไหน

> **อัปเดต D98:** ทีม SES แก้สคริปต์ให้แล้วเป็น v2 (อ่าน `paymentTypes`, ลูกค้าใหม่/ไม่มีวิธีชำระเปิดบิลพักได้, ไม่ตรวจอุปกรณ์เสริม,
> ใช้ record ล่าสุด, พนักงานที่ไม่พบเว้นว่าง) และเพิ่ม `ses_report_bill` ไฟล์และรายการที่เปลี่ยนอยู่ที่ [fmp-scripts/README.md](fmp-scripts/README.md)
> ตารางด้านล่างคือผลตรวจของ **ต้นฉบับ v1** เก็บไว้เป็นเหตุผลของการแก้

อ่านจากไฟล์ `ses.rtf` และ `ses_fail.rtf` ที่ทีม FMP ส่งมา (2026-11-02) เทียบกับข้อมูลที่ SES ส่งตอนนี้

**สรุป: สคริปต์ใช้งานได้แล้ว ไม่ต้องเขียนใหม่** (รวมออเดอร์ที่มีอุปกรณ์เสริม เพราะ SES ส่ง `accessories` ว่างแล้ว) ส่วนที่ควรปรับคือ
ลูกค้าใหม่ วิธีชำระ และกรณีตามตารางในข้อ 5

| ขั้นในสคริปต์ | ผลกับข้อมูลของ SES |
| --- | --- |
| parameter = SES ID, หา `ses_id` ต้องเจอ 1 record | ผ่าน (SES ส่ง reference และรักษา 1 record ต่อออเดอร์) |
| `ses_status` = DONE / PROCESSING | ผ่าน (กันทำซ้ำได้ถูกต้อง) |
| `reference` = parameter, `version` = 1, `state` = SENT_TO_CASHIER | ผ่าน (ยกเว้น ADMIN สั่งส่งซ้ำหลังแคชเชียร์รับของแล้ว จะได้ `INVALID_STATE` ซึ่งถูกต้อง) |
| `test` + `$ALLOW_TEST` | ผ่าน (SES ส่ง `test: false` เสมอ ตั้ง `$ALLOW_TEST = 0` บน production ได้เลย) |
| เบอร์ลูกค้าต้องมีในตาราง `customer` | **ไม่ผ่านสำหรับลูกค้าใหม่** (`WRONG_PHONE`) |
| `branch.code` ต้องมีในตาราง `branch` | ผ่าน (รหัสสาขาตรง ERP แล้ว) |
| `payments` ต้องไม่ว่าง | **ไม่ผ่านถ้าพนักงานไม่ได้เลือกวิธีชำระ** (`NO_PAYMEN`) SES ไม่บังคับเลือก |
| แปลง `payments` ด้วย Substitute คำอังกฤษ | **ได้ข้อความผิด** เช่น `0% Credit Card` กลายเป็น "0% บัตรเครดิต…" แทนบัตรเงินผ่อน, `PayNext`/`WEB` ไม่ถูกแปลง |
| `accessories` ต้องว่าง | ผ่าน (SES ส่ง `[]` เสมอ อุปกรณ์เสริมอยู่ที่ `accessoriesForCashier` ให้หน้าร้านเพิ่มเอง) |
| `items` ต้องไม่ว่าง, `sn` ครบตาม `quantity` | ผ่าน (SES บังคับให้ STOCK สแกนครบ ไม่ซ้ำ) |
| SN ต้องมีในสต็อก ready สาขาเดียวกัน รุ่นตรง มีราคา ยังไม่ขาย/พัก | ผ่านถ้า STOCK สแกนเครื่องจริงของสาขานั้น (SES ส่ง SN เป็นตัวใหญ่ตามที่สแกนจากกล่อง) |
| `staffId` → `GetAsNumber` | ผ่านสำหรับพนักงานจาก ERP ส่วนบัญชีที่สร้างเองใน SES (เช่น `0001`) จะได้เลขที่ไม่ใช่พนักงานจริง |
| `createdAt` → Timestamp | ผ่าน (รูปแบบ `YYYY-MM-DDTHH:mm:ss+07:00`) |
| ผลลัพธ์ JSON `{ok, code, sesID, saleID, lines, …}` และ `ses_fail` | ผ่าน **SES อ่านผลนี้แล้ว** และแสดงในหน้า Admin เช่น `CREATED saleID …` หรือ `SN_NOT_FOUND: …` (กรุณาคงรูปแบบ JSON นี้ไว้) |

## 5. สิ่งที่ทีม FMP ควรปรับ (เรียงตามความสำคัญ)

> **อัปเดต D98:** ข้อ 2, 3, 4, 6, 7 ทีม SES แก้ในสคริปต์ v2 ให้แล้ว ที่เหลือให้ทีม FMP: เติม PayBy ของ Trade In / U-Joy / Partner Mall / อื่นๆ,
> บิลพักเดิมเมื่อแคชเชียร์ตีกลับ (ข้อ 5), index ของ `product_sn` (ข้อ 8), ลบ record ทดสอบ (ข้อ 9) และจุดเรียก `ses_report_bill`

| # | เรื่อง | ทำไม | ข้อเสนอ |
| --- | --- | --- | --- |
| — | ~~อุปกรณ์เสริม~~ | ตกลงแล้ว (2026-11-03): หน้าร้านเพิ่มเองใน FMP | ไม่ต้องแก้สคริปต์ SES ส่ง `accessories` ว่าง ถ้าอยากแสดงเป็นหมายเหตุ อ่านจาก `accessoriesForCashier` ได้ (ไม่บังคับ) |
| 2 | **วิธีชำระเงิน** | Substitute คำอังกฤษบน `payments` ให้ค่าผิด | อ่าน **`paymentTypes`** แทน แล้วจับคู่ 1:1 ตามตารางด้านล่าง |
| 3 | **ลูกค้าใหม่** (`WRONG_PHONE`) | ลูกค้าครั้งแรกยังไม่มีใน `customer` | ตัดสินใจฝั่ง FMP: สร้างลูกค้าใหม่จากเบอร์อัตโนมัติ หรือให้แคชเชียร์สร้างแล้วกด "ส่งซ้ำ" ใน SES (record เดิมจะถูกประมวลผลใหม่ เพราะสถานะเป็น ERROR) |
| 4 | **ไม่มีวิธีชำระ** (`NO_PAYMEN`) | SES ไม่บังคับเลือกวิธีชำระ | ยอมให้บิลพักไม่มี PayBy (แคชเชียร์ใส่ตอนรับเงิน) หรือแจ้ง SES ว่าต้องบังคับ (SES ปรับได้) |
| 5 | **บิลพักเดิมเมื่อแคชเชียร์ตีกลับ** | ถ้าบิลพักสร้างไปแล้ว (DONE) แล้ว STOCK สแกนเครื่องใหม่ส่งมา สคริปต์ตอบ `ALREADY_DONE` และ SN ใหม่ไม่ถูกใช้ (SES แสดงเป็น error) | เมื่อได้ record เดิมที่ `ses_body` เปลี่ยน (ดู `outboxId` ใหม่) ให้ยกเลิกบิลพักเดิมแล้วสร้างใหม่ หรือให้แคชเชียร์ยกเลิกบิลพักเดิมแล้วตั้ง `ses_status` เป็นว่าง แล้ว ADMIN กดส่งซ้ำ |
| 6 | หา record ด้วย `ses_id` | SES รักษา 1 record ต่อออเดอร์อยู่แล้ว | กันไว้อีกชั้น: ถ้าเจอมากกว่า 1 ให้ใช้ record ล่าสุด แทนการตอบ `NOT_FOUND` |
| 7 | `staffId` | บัญชีสร้างเองใน SES ไม่ใช่รหัสพนักงาน ERP | ถ้าแปลงไม่ได้ ให้เว้นว่างหรือใช้ค่า default แทน |
| 8 | ความเร็ว | SES รอคำตอบสคริปต์ไม่เกิน 60 วินาที | ให้ `product_sn` ใน `ProductStore_detail` มี index |
| 9 | record ทดสอบเก่า | ตาราง `ses` มี 4 record ทดสอบ (SES-TEST-00001/2, SES-20261030-000001/2) | ลบได้ ไม่มีออเดอร์จริงใน SES ผูกอยู่แล้ว |

| --- | --- |
| เงินสด | เงินสด ( Cash ) |
| โอนเงิน | โอนเงิน ( Bank Transfer ) |
| บัตรเครดิต | บัตรเครดิต ( Credit Card ) |
| บัตรเงินผ่อน | บัตรเงินผ่อน (Card Installment) |
| ใช้มัดจำ | ใช้มัดจำ (Deposit) |
| Trade In | (ทีม FMP เติม) |
| U-Joy | (ทีม FMP เติม) |
| Partner Mall | (ทีม FMP เติม) |

## 5.1 เครื่องอยู่ที่ร้านแล้ว แต่ FMP ยังไม่อัปเดต (สคริปต์ `ses` v3, 2026-11-05)

เคสจริง (B001, 2026-11-05): สินค้าโอนจาก ISTM (สาขา 16) มาถึง ISTA แล้ว แต่ใน FMP ยังไม่กดรับโอน สคริปต์ตอบ `SN_WRONG_BRANCH` และ
**ปฏิเสธทั้งออเดอร์** ร้านขายต่อไม่ได้ SES ไม่ได้ถือสต็อกระดับ SN (FMP เป็นข้อมูลจริงที่เดียว) จึงแก้สองฝั่ง:

1. **SES:** STOCK กด "ส่งโดย SN ยังไม่ครบ" ได้ (ต้องยืนยันอีกครั้ง) เครื่องที่ไม่มี SN ส่งเป็น `snMissing` ใน `items`
2. **สคริปต์ `ses` v3** ([fmp-scripts/ses_v3.txt](fmp-scripts/ses_v3.txt)) สวิตช์ `$ALLOW_SN_LATER = 1`:
   - เครื่องที่ไม่มี SN และ SN ที่ FMP ยังไม่มีในสาขานี้ (`SN_NOT_FOUND`, `SN_WRONG_BRANCH`, `SN_NOT_READY_FOR_SALE`) **เปิดบรรทัดโดยไม่มี SN**
     (ราคา/ชื่อจากรุ่นใน `ProductStore`) แทนการปฏิเสธทั้งออเดอร์ ชื่อบรรทัดต่อท้าย "(รอสแกน SN)"
   - SN รุ่นไม่ตรง, ขายแล้ว / อยู่ในบิลพักอื่น, ซ้ำ **ยังปฏิเสธ** (หยิบผิดเครื่อง ให้ Stock สแกนใหม่)
   - ผลลัพธ์ `code` = `CREATED_SN_LATER`, `snPending` = จำนวนเครื่องที่รอสแกน, `message` บอกเหตุผล SES แสดงเป็นคำเตือนสีเหลืองให้แคชเชียร์
3. **แคชเชียร์:** สแกน SN ของบรรทัดนั้นใน FMP ตอนรับเงิน เครื่องที่โอนมาต้อง **รับโอนใน FMP ก่อน** (สต็อกของ FMP ยังต้องถูก)

**คำถามถึงทีม FMP:** หน้าบิลของ FMP ให้แคชเชียร์สแกน SN ใส่บรรทัดที่ยังไม่มี SN ในบิลพักได้ไหม ถ้าไม่ได้ ต้องลบบรรทัดนั้นแล้วสแกนเพิ่มใหม่
(บอก SES ได้ จะปรับคำแนะนำบนหน้าจอ) และชื่อฟิลด์ใน SQL ของ `$partRow` ให้ใช้ชื่อเดียวกับ SQL ของ `$snRow` (ส่วนที่ export ตัดไป)

## 6. FMP แจ้งกลับ SES

### 6.1 ผลของสคริปต์ (อัตโนมัติ ไม่ต้องทำอะไรเพิ่ม)

ทุกครั้งที่ SES สร้างหรือแก้ record และสั่งสคริปต์ `ses` SES อ่านผล JSON ที่สคริปต์คืน (`Exit Script`) และแสดงที่ Admin → ส่งไป FileMaker
`ok: true` = สำเร็จ (เช่น `CREATED saleID …`), `ok: false` = error พร้อม `code` และ `message` (`SN_NOT_FOUND`, `WRONG_PHONE` …)

### 6.2 เมื่อเปิดบิล และเมื่อชำระเงินเสร็จ (แนะนำให้ทำ): บอก SES ด้วยเวลาจริง

SES เก็บเวลาทุกขั้นตามจริงเพื่อวัดว่าลูกค้ารอนานแค่ไหน แคชเชียร์กดปุ่มใน SES ช้ากว่าเหตุการณ์จริงเสมอ (หรือลืมกด) เวลาที่ดีที่สุดจึงมาจาก FMP
ตอนที่เหตุการณ์เกิดจริง ใช้สคริปต์สำเร็จรูป [`ses_report_bill`](fmp-scripts/ses_report_bill.txt) (v2) ได้เลย (ตั้งค่า User-Agent และรูปแบบเวลาไว้แล้ว)
เรียก 2 จุดในบิลพักที่มาจาก SES:

| จุดที่เรียก | Parameter | ผลใน SES |
| --- | --- | --- |
| ก. แคชเชียร์เปิดบิลพักขึ้นมาทำรายการ | `{ "sesID": "…", "billNo": "…" }` | **"เปิดบิลแล้ว" (BILL_OPENED)** ด้วยเวลานั้น + แสดงเลขบิล |
| ข. รับชำระเงิน / ออกใบเสร็จเสร็จ | `{ "sesID": "…", "billNo": "…", "paid": 1 }` | **"ปิดการขาย" (COMPLETED)** ด้วยเวลาที่ชำระ |

ถ้าเรียกได้จุดเดียว ให้เรียกที่ ข. (SES บันทึกเปิดบิลและปิดการขายเป็นเวลาเดียวกัน) เรียกทันทีที่เกิดเหตุการณ์ ห้ามเก็บไว้เรียกย้อนหลัง
เพราะเวลาที่ส่งคือเวลาตอนสคริปต์รัน หรือเรียกเองตามนี้:

```
POST https://ses.uficon.com/api/integrations/pos/bills
Authorization: Bearer <POS_API_KEY>
Content-Type: application/json

{ "reference": "SES-20261103-000001", "billNo": "<เลขที่บิลใน FMP>", "openedAt": "2026-11-03T14:52:10+07:00" }
{ "reference": "SES-20261103-000001", "billNo": "<เลขที่บิลใน FMP>", "openedAt": "2026-11-03T14:58:40+07:00", "completedAt": "2026-11-03T14:58:40+07:00" }
```

- บรรทัดแรก = จุด ก. บรรทัดที่สอง = จุด ข. (`completedAt` = เวลาที่ชำระ; `openedAt` SES ใช้เฉพาะครั้งแรกที่ได้ยินเลขบิลนี้)
- แคชเชียร์ไม่ต้องกดใน SES ปุ่ม "เปิดบิล" / "ปิดการขาย" ใน SES ยังอยู่สำหรับตอนที่ FMP ยังไม่ได้เรียก
- เรียกซ้ำด้วย reference + เลขบิลเดิมได้ (ได้ 201 เหมือนเดิม ไม่บันทึกซ้ำ) ถ้าเลขบิลต่างจากที่เคยแจ้ง ได้ 409
- เวลาใส่เวลาไทยพร้อม `+07:00` เวลาที่ไม่สมเหตุผลได้ 400: ก่อนลูกค้าเข้าร้าน, ชำระก่อนเปิดบิล, หรือล้ำเวลาปัจจุบันเกิน 5 นาที
  (นาฬิกาเซิร์ฟเวอร์ FMP ต้องตรง)
- คีย์ `POS_API_KEY` ขอจากเจ้าของระบบ SES (ห้ามวางในแชตหรือ issue) ไม่มีคีย์หรือคีย์ผิดได้ 401
- ฝั่ง FileMaker: ใช้ *Insert from URL* กับ cURL options เช่น
  `-X POST -A "Mozilla/5.0 (FileMaker; UFicon SES bill report)" -H "Content-Type: application/json" -H "Authorization: Bearer " & $key -d @$json`
- **ต้องใส่ User-Agent ที่ไม่ใช่ของ curl** Cloudflare หน้า ses.uficon.com ตอบ 403 กับ user-agent ของ curl (ทดสอบแล้ว 2026-11-03)

### 6.3 รายงานสถานะอื่นๆ (ไม่บังคับ)

`POST https://ses.uficon.com/api/integrations/fmp/callback` (คีย์ `FMP_CALLBACK_KEY`) ใช้รายงานผลพร้อมข้อความและเวลา เช่นเมื่อรับเงินแล้ว
SES บันทึกไว้แสดงในหน้า Admin เท่านั้น ไม่เปลี่ยนสถานะออเดอร์ รายละเอียดใน [fmp-outbound.md](fmp-outbound.md) หัวข้อ "Reporting back"

## 7. ทดสอบครั้งแรก

1. SES ADMIN เช็กหน้า Admin → ส่งไป FileMaker ว่า "สคริปต์ที่เรียกต่อ: ses"
2. ใช้ลูกค้าที่มีอยู่แล้วใน FMP (เบอร์ใน `customer`) สาขา **ISTA** สินค้ามี SN สถานะ ready ที่สาขานั้น (เช่น MacBook `MGEA4TH/A` SN `SML4K3429G5`)
   เลือกวิธีชำระ 1 อย่าง (อุปกรณ์เสริมใส่ได้ หน้าร้านเพิ่มลงบิลใน FMP เอง)
3. STOCK สแกน SN แล้วกดส่ง ภายในประมาณ 10 วินาทีควรเห็นผลในหน้า Admin ของ SES และ record ในตาราง `ses` ของ FMP
4. บิลพักที่สร้างเป็นของจริงใน FMP ทีม FMP ลบหรือยกเลิกหลังทดสอบ

## 8. ติดต่อ / ข้อควรระวัง

- รหัสผ่านบัญชี `ses` และคีย์ทั้งหมดส่งกันนอกแชต ถ้าเคยวางในแชตแล้วควรเปลี่ยน
- SES ส่งแบบ "อย่างน้อยหนึ่งครั้ง" (at-least-once) และรักษา 1 record ต่อออเดอร์ สคริปต์จึงควรทนการถูกเรียกซ้ำ (ตอนนี้ทำได้แล้วด้วย `ses_status`)
